Децентрализованная сеть garageAlarms

Forge-сессия · 29.09.2026 · идея укреплена и готова к архитектуре

Главная находка

Telegram — арбитр лидерства. Дубль в Telegram возможен только если оба узла до него достучались — а тогда 409 Conflict на getUpdates сам выдаёт второго лидера, даже при разорванной внутренней сети. Отдельный etcd/кворум не нужен.

Зафиксированные решения

  • Децентрализация без хаба; модель AP, eventual consistency. Дубль допустим — потеря нет.
  • Логические узлы (2..N, ESP32 + FRAM): реплика очереди, конфиг и правила, веб, Telegram. Один LEADER, остальные FOLLOWER.
  • Коллекторы: только датчики и пересылка, маленький буфер до подтверждения, не голосуют.
  • Мягкий лидер — наименьший живой ID по gossip-членству; лидер нужен только против дублей.
  • Доставка «хотя бы один раз»: коллектор → все логические узлы; ID = узел + счётчик; дедуп.
  • ISOLATED-узел шлёт тревоги сам в аварийном режиме.
  • Постоянная память — FRAM. Провода датчиков — оконечные резисторы + АЦП.

Отвергнуто

  • Zigbee на ESP32-S3 — нет радио 802.15.4; нужен H2/C6 или внешний модуль.
  • SSD/SD как постоянная память — FRAM проще и выдерживает ~10¹⁴ перезаписей.
  • Raft, строгий кворум, обязательный 3-й узел — лишние при AP-модели.
  • Готовые Zigbee-датчики — у пользователя свои проводные немецкие и Panasonic.
  • Второй внешний канал (LTE/SMS, сирена) — отложен: Telegram работает.

Слабые места, пережившие проверку

  • Нужен long polling (timeout≈20с): сейчас timeout:0 — 409 не возникает, арбитраж не сработает.
  • offset Telegram живёт в RAM — реплицировать; команды идемпотентны, иначе новый лидер повторит /reboot.
  • LWW молча теряет одновременную правку одного правила — показывать конфликт в вебе.
  • Telegram — единственный внешний канал.
  • Текущий NVS 20 КБ изнашивается очередью в худшем сценарии — снимается переходом на FRAM.
