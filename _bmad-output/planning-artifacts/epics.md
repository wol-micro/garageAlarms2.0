# garageAlarms 2.0 - Epic Breakdown

## Overview

This document provides the complete epic and story breakdown for garageAlarms 2.0, decomposing the requirements from the SPEC (в роли PRD) and Architecture spine into implementable stories. Целевой репозиторий — `garageAlarms2.0`.

Общее правило: начиная с истории 2.7 каждая история, меняющая поведение акторов, добавляет свои инварианты в детерминированный симулятор сети (AD-27) и проходит его.

## Requirements Inventory

### Functional Requirements

FR1 (CAP-1): Узел описывает свои каналы (имя, зона, назначение, тип `binary|numeric|counter|enum`, критичность) и публикует описание при смене версии, состояние — при изменении и периодически.
FR2 (CAP-1): Канал имеет здоровье `ok|fault|open|short|stale`; шлейфы с оконечным резистором через ADS1115 различают норму, тревогу, обрыв и КЗ.
FR3 (CAP-1): Шлюз драйверов 1-Wire и I²C: новый датчик добавляется файлом драйвера по общему интерфейсу и перекомпиляцией; скомпилированные датчики находятся автоматически (ROM ID; адрес + `probe`) и появляются в вебе как каналы «без имени»; стартовый набор — `sensor-catalog.md`.
FR4 (CAP-1): Цифровые входы — антидребезг по времени с cooldown; прогрев только для PIR; дым без прогрева.
FR5 (CAP-1, CAP-9): INA219 на коллекторе контролирует линию 12 В датчиков; пропадание или просадка — `fault` критичного канала.
FR6 (CAP-1): Наличие 220 В на логическом узле — `binary`-канал через оптронный модуль.
FR7 (CAP-2): Коллектор отправляет событие каждому живому логическому узлу и повторяет каждому до его ACK или объявления узла мёртвым; неподтверждённое событие переживает перезагрузку коллектора.
FR8 (CAP-2): Zigbee-mesh в режиме distributed security без координатора; коллектор доставляет событие через соседа без прямой видимости логического узла.
FR9 (CAP-3): Логические узлы реплицируют исходные события (anti-entropy по `(node, boot)` → `seq`), исходящую очередь, мягкий конфиг и состояние `Notify` (`offset`, receipts, `delivered`, `ack`).
FR10 (CAP-3): Очередь и конфиг хранятся в FRAM; после отключения питания всех узлов неотправленное уходит с пометкой «с опозданием»; правка правила на узле A видна на B ≤ 1 мин.
FR11 (CAP-4): Лидер вычисляется каждым узлом: среди узлов со здоровым uplink (гистерезис N/M) — мин. `leader_priority`, затем мин. EUI-64; возврат приоритетному после 15 мин стабильного uplink; `leader_override{node, until}` действует сразу.
FR12 (CAP-4): Аренда лидера — закреплённое сообщение `lease{node, priority, until}` в чате владельца; при 409 узел читает аренду через `getChat` и уходит в `YIELDED` или забирает просроченную; без аренды — пауза `base × (1 + ранг)`.
FR13 (CAP-4): `FOLLOWER` отправляет недоставленные единицы критичного события через T; узел без пиров, но с uplink — `LEADER`; `ISOLATED` (нет пиров и uplink) только копит.
FR14 (CAP-5): Подписчики получают события в Telegram; каждое сообщение подписано узлом и статусом; между отправками пауза; пролежавшие помечены «с опозданием».
FR15 (CAP-5): Критичные события дублируются в Pushover `priority=2`, `tag = event_id`; лишние копии — `cancel_by_tag`; receipt опрашивается, подтверждение → `ack`.
FR16 (CAP-5): Подтверждение в любом канале (`ack{event_id, by}`) гасит повторы во всех каналах; длящийся дым напоминается каждые 15 мин до подтверждения/окончания.
FR17 (CAP-5): Единица доставки `(event_id, recipient, channel)`; `delivered` публикует отправивший узел; элемент удаляется, когда все единицы доставлены или окончательно отклонены.
FR18 (CAP-6): Движок исполняет 9 шаблонов правил (`rule-templates.md`) на каждом логическом узле детерминированно по `ts` источника.
FR19 (CAP-6): Условие `when` по принятой грамматике, проверка при сохранении (≤ 256 символов, ≤ 8 уровней).
FR20 (CAP-6): Наборы правил и режимы («дома», «уехал», «ночь») включают и выключают наборы.
FR21 (CAP-6): Производное событие имеет ID `rule_id@window_start`; одинаково на всех логических узлах; окна восстанавливаются после перезагрузки из хранимых исходных событий.
FR22 (CAP-6): Команды правил («опросить сейчас», burst-интервал) несут ID и TTL и откатываются сами.
FR23 (CAP-7): Локальный веб: имена, зоны, назначение, критичность, пороги, интервалы, правила, режимы, граф зон, `leader_priority`, `leader_override`, подписчики; показ конфликтов правок.
FR24 (CAP-7): Веб: экспорт/импорт мягкого конфига, «забыть узел»; выключение критичного правила только временно (по умолчанию 2 ч, максимум 12 ч) с оповещением всех подписчиков.
FR25 (CAP-8): Команды Telegram из `external-channels.md`: подписка по PIN, статус (лидер, узлы, каналы), отчёты, тест, «Принято», mute некритичного, `/leader`, `/reboot`; опасные — только владелец с подтверждением; правила из Telegram не меняются.
FR26 (CAP-8): Команды идемпотентны по `update_id`; `offset` реплицируется до исполнения команды.
FR27 (CAP-9): События «узел пропал», канал `stale`/`open`/`short`, потеря uplink; для критичного канала — критичные.
FR28 (CAP-9): Ежедневный отчёт «жив» владельцу; уведомление о перезагрузке с причиной сброса (≤ 1 за 15 мин неожиданных, ≤ 1 за 6 ч плановых); расхождение `GA_CONFIG_VERSION` — событие здоровья.
FR29 (CAP-10): Ввод узла по USB: раздел секретов (ключ сети, роль, WiFi, внешние секреты) записывается при прошивке.
FR30 (CAP-10): Ввод по BLE: окно ограничено, Security 2; S3 — `network_provisioning`, H2 — `protocomm` со своим endpoint; только пока Zigbee не запущен.
FR31 (CAP-11): OTA логического узла по UDP через веб, вместе с RCP-прошивкой его H2; откат, если новая прошивка не вошла в сеть.
FR32 (CAP-11): OTA коллекторов по Zigbee OTA Upgrade cluster, сервер — `LEADER`; по одному узлу; запасной путь — своя передача образа через L2 (`bulk`).
FR33 (CAP-12): MQTT-зеркало: темы `state` (retained), `events`, `health`; JSON с `event_id`; QoS 1; отдельный ограниченный буфер FRAM; адрес/порт/TLS/префикс — мягкий конфиг, логин/пароль — на узле.
FR34 (CAP-13): Кадр `[body, kid, m]` с HMAC по сырым байтам; антиповтор битовой картой `seq` на `(node, boot)`; смена ключа через `kid`.
FR35 (CAP-13): Секреты в зашифрованном NVS; OTA-образ только с валидной подписью; в серийном исполнении secure boot v2 (RSA-3072) + flash encryption на логических узлах.
FR36 (CAP-3, CAP-7): Мягкий конфиг (подписчики, mute, имена, зоны, критичность, приоритеты, правила) хранится через `Storage` и реплицируется между логическими узлами: версия на ключ, LWW по HLC, надгробия; доступен акторам до появления веб-редактора.
FR37 (CAP-14): Канал `output` подтипов `switch` и `buzzer` на коллекторе: подтверждение второй парой контактов, `max_on`, предел зуммера, безопасное состояние `off | hold` при старте и потере связи (AD-29).
FR38 (CAP-14): Узел выхода сам выбирает действующую команду: слоты `protect > manual > auto` по `ts`, `release`, дедуп по `cmd_id`; команды шлёт каждый логический узел, без лидера.
FR39 (CAP-6, CAP-14): Действие правил «установить выход»: `cmd_id = rule_id@event_id`, `ts` причины, уровень по критичности канала.
FR40 (CAP-8, CAP-14): Ручное управление выходами из веба и бота через реплицируемое `output_intent`; в боте — владелец и операторы, выходы с `bot_control`.
FR41 (CAP-14): Локальные правила на коллекторе: «своё событие → свой выход» без окна и `when`, таблица с версией в NVS и heartbeat, работает при выключенных логических узлах.
FR42 (CAP-12, CAP-14): Входящий MQTT для выходов с `mqtt_control`: MQTT-узел, `clean_start`, отбрасывание retained и старых команд, PUBACK после записи намерения, страховка ведомых, темы `set` и `result`.

### NonFunctional Requirements

NFR1: Приоритет: не потерять событие > не флудить > остальное; доставка «хотя бы один раз», при переключении лидера ≤ 1 дубль.
NFR2: Критичная тревога доходит в Telegram и Pushover ≤ 60 с при отказе лидера или коллектора-ретранслятора; при отказе роутера — без потерь и ≤ 60 с после возврата интернета.
NFR3: Совместимость протокола N и N−1; незнакомые поля и типы пропускаются, незнакомые события хранятся непрозрачно.
NFR4: Никакого ожидания без таймаута «без прогресса»; все задачи в task watchdog; TLS только после синхронизации времени.
NFR5: Сообщение состояния канала укладывается в один Zigbee-кадр (~80 байт).
NFR6: Объёмный трафик не душит Zigbee-mesh: `bulk` — UDP, по Zigbee только с ограничением скорости.
NFR7: Все таймауты и константы — только в `ga_config.h`; стартовые значения — `tunables.md`.
NFR8: Тексты пользователю — русский; код, комментарии, логи — английский.
NFR9: Полная настройка — только локальный веб; внешние секреты не передаются по сети.
NFR10: Все узлы от сети; коллекторы — Zigbee-роутеры.
NFR11: Mute никогда не глушит критичное.
NFR12: Коробка 1.x работает до ввода новой сети.

### Additional Requirements

- **Стартового шаблона нет** — Epic 1 Story 1: новый репозиторий `garageAlarms2.0`, монорепо ESP-IDF v6.0.x: `components/` (`ga_config`, `proto`, `mesh`, `delivery`, `membership`, `storage`, `sensors`, `sys`, `config`, `rules`, `notify`, `ui`) + `apps/logic-s3`, `apps/collector-h2`; сборка обеих прошивок.
- Пины версий: ESP-IDF v6.0.x, esp-zigbee-lib 2.0.4, espressif/cbor 7.0.0, espressif/network_provisioning 1.2.5, espressif/mqtt 1.0.0.
- Каркас акторов (AD-1, AD-2): задача + входная очередь на актор, запрос/ответ по `corr_id`, события по подписке; направление зависимостей по диаграмме каркаса.
- `Storage` — единственный доступ к FRAM (SPI) / NVS; запись до подтверждения (AD-4).
- `proto` — единственный источник кадра, конверта (`v, t, c, k, n, b, q, ts, p`), классов трафика, критичности, версий; печать через `cborjson` (AD-5, AD-6).
- `Mesh`: Zigbee через H2 RCP по UART на логическом узле, нативный стек на H2-коллекторе; UDP по LAN; выбор канала по классу (AD-12, AD-13).
- `Membership`: heartbeat с ролью, статусом, uplink, `uplink_since`, `leader_priority`, сводкой версий, здоровьем каналов, временем, `GA_CONFIG_VERSION` (AD-19, AD-25).
- `Config`: версия на ключ, LWW по HLC `(wall_ms, counter, EUI-64)`, надгробия (AD-14).
- Время: NTP на логических; без NTP — от `LEADER`; коллекторы — из heartbeat (AD-20).
- Host-тесты `proto`/`delivery` на Linux-таргете ESP-IDF — до первого эпика с `proto`.
- Проверки прототипа: связь S3↔H2 RCP; Zigbee OTA-сервер на роутере в distributed-сети; потери Zigbee под нагрузкой WiFi/TLS.
- Стенд по `bill-of-materials.md`: 2 логических + 2 коллектора.

### Accepted Limitations

- До эпика 5 нет временного выключения критичного правила (FR24); на стенде сломанный критичный датчик глушится только подтверждением (FR16). Рабочая сеть вводится в эпике 6, уже с вебом.

### UX Design Requirements

Источник: `ux-designs/ux-garageAlarms-2026-09-30/DESIGN.md` и `EXPERIENCE.md` (макеты — `mockups/`). Каждое UX-DR привязано к историям; при реализации истории её UX-DR входят в критерии приёмки.

#### Telegram-бот

- UX-DR1 → 4.1: неподписанный чат на любую команду, кроме `/subscribe`, получает только «Чтобы получать тревоги: /subscribe PIN»; верный PIN — «Вы подписаны. Тревоги придут сюда.» и меню подписчика; неверный — «Неверный PIN.»; лимит — «Список подписчиков заполнен — обратитесь к владельцу.»
- UX-DR2 → 4.2, 4.7: `/menu` и `/start` присылают главное меню; кнопки по роли (подписчик: Датчики, События, Статус, Отчёт, Тест, 🔕 Моя тишина, Отписаться; оператор: + Режим; владелец: + 🔇 Общая тишина, Ведущий, Перезагрузка, Статистика, без Отписаться).
- UX-DR3 → 4.2: нажатие кнопки меню правит то же сообщение (`editMessage` с `parse_mode=HTML`) и вызывает `answerCallbackQuery`; новое сообщение меню — только по `/menu`; каждый экран кончается `‹ Меню`.
- UX-DR4 → 4.2, 8.9: роль проверяется при нажатии по `from.id`; кнопка чужой роли отвечает «Эта команда доступна владельцу.» / «Смена режима доступна владельцу и операторам.» и ничего не исполняет.
- UX-DR5 → 4.2: первая строка главного меню — `🟢 Всё спокойно · режим «…»` или `🚨 Активна тревога: <тип> · <зона>`, плюс `🔇 общая тишина до ЧЧ:ММ` и (только своему чату) `🔕 моя тишина до ЧЧ:ММ`.
- UX-DR6 → 4.7, 7.1: «Датчики» — по зонам; если не помещается в одно сообщение, сначала зоны кнопками; строка канала `<точка> <тип> <имя> — <состояние>`; binary — `· последний раз <дата время>` (или «ни разу»); numeric — `<значение с единицей> · сутки <мин>…<макс>` (сутки — 7.1) с десятичной запятой; numeric у порога — 🟡 рядом со значком типа.
- UX-DR7 → 4.7, 7.9: неисправный канал в «Датчиках» — 🟣 со словом (`обрыв`/`КЗ`/`неисправен` с ЧЧ:ММ), молчащий — ⚪ `молчит N мин`.
- UX-DR8 → 4.7: «События» — блок «Сейчас» (активные: «не подтверждено» / «принято: кем») и история с листанием `‹ Раньше` / `Позже ›` в том же сообщении, по N событий (значение — `tunables.md`, старт 10).
- UX-DR9 → 4.2: «Статус» и `/status` — ведущий, узлы на связи с uplink, пропавшие «пропал N мин назад», режим, общая тишина, неисправные каналы.
- UX-DR10 → 4.7: «Статистика» — только владельцу, за 7 дней: подписчики с ролями, перезагрузки по узлам с причинами, отказы (пропадания узлов, ошибки доставки, неисправности каналов).
- UX-DR11 → 4.2, 8.9: `/leader`, `/reboot`, `/mode`, отписка — экран выбора → экран последствия с `[✅ Подтвердить] [✖ Отмена]`; подтверждение устаревает (срок — `tunables.md`, старт 2 мин) с ответом «Время подтверждения вышло, повторите.» и не исполняется.
- UX-DR12 → 4.2, 5.7: попытка изменить правило, конфиг или выключить тревоги канала из Telegram получает «Правила меняются только в локальном вебе.»
- UX-DR13 → 4.3: каждое сообщение бота кончается строкой `🏠 <имя узла> · <статус по-русски>` (например `🏠 гараж · ведущий`; ведущий/ведомый/уступил/изолирован).
- UX-DR14 → 4.3: сообщение, пролежавшее в очереди дольше порога, второй строкой несёт `⏳ с опозданием · событие в ЧЧ:ММ`.
- UX-DR15 → 4.3: первая строка события — один значок важности (🚨 ⚠️ 🔧 ✅ ℹ️) и значок типа (🔥 💧 🌡 🚶 🔌 📟); ЗАГЛАВНЫЕ — только в заголовке критичной тревоги.
- UX-DR16 → 4.3, 4.5: критичная тревога — новое сообщение: `🚨 <тип> <b>ТИП · ЗОНА</b>`, «Сработал в ЧЧ:ММ.», тренд зоны за окно правила скорости изменения (по умолчанию 10 мин; строки нет без числового канала), `Соседние зоны: <точка> <зона> — <худшее состояние>` через « · » по графу зон (строки нет без соседей), «Не подтверждено.», кнопки `[✅ Принято] [📋 Статус]`.
- UX-DR17 → 4.5: «Принято» из Telegram или Pushover правит сообщение тревоги у всех получателей: кнопки убраны, строка статуса — `✅ Принято: <кто>, ЧЧ:ММ. Повторы остановлены.`; повторы и Pushover прекращаются.
- UX-DR18 → 4.5: длящийся неподтверждённый дым каждые 15 мин даёт новое `🔁 🔥 ДЫМ всё ещё · <ЗОНА> — N мин с начала, не подтверждено` с трендом и теми же кнопками; окончание — `✅ 🔥 Дым в <зоне> прекратился · ЧЧ:ММ`.
- UX-DR19 → 4.5: «🔕 Моя тишина» — `[1 ч] [4 ч] [8 ч] [Выключить]`; до срока некритичное этому чату — без звука, критичное — со звуком; снимается само; экран говорит «Критичные тревоги всё равно зазвонят.»
- UX-DR20 → 4.5: «🔇 Общая тишина» и `/mute N` — только владельцу, не больше `MAX_MUTE_HOURS`; ответ «Некритичное не отправляется до ЧЧ:ММ. Тревоги придут.»

## Epic List

### Epic 1: Прототип подтверждает железо и Zigbee
Владелец знает, что выбранное железо и Zigbee-подход работают, до того как в них вложено основное время: связь S3↔H2 (RCP), сеть distributed security, созданная роутером, потери Zigbee под нагрузкой WiFi/TLS, Zigbee OTA с сервером на роутере; host-тесты `proto` на Linux-таргете. Итог — отчёт «подтверждено / нужен запасной путь» по каждому риску; завершающая история-шлюз заносит итоги в каркас и спецификацию (при необходимости `bmad-correct-course`).
**FRs covered:** FR8 (проверка), FR32 (проверка), FR34 (host-тесты)

### Epic 2: Первая тревога проходит через сеть
Сухой контакт на коллекторе H2 доходит по Zigbee-mesh (через соседа) до логического узла S3+H2, записывается в FRAM и приходит в Telegram. Узлы вводятся по USB, секреты хранятся в зашифрованном NVS, кадры подписаны.
**FRs covered:** FR4, FR7 (один узел), FR8, FR10 (FRAM), FR14 (базово), FR29, FR34, FR35 (секреты)

### Epic 3: Нет единой точки отказа
Два логических узла: heartbeat и живость, выбор лидера с арендой в Telegram, репликация событий, очереди, состояния `Notify` и мягкого конфига, второй путь по UDP, страховка критичного. Разметка FRAM имеет версию и миграцию и хранит историю исходных событий с запасом под окна правил. Завершается стендовым хаос-тестом из критерия успеха: отключение лидера, роутера, ретранслятора — тревога ≤ 60 с, без потерь, ≤ 1 дубля.
**FRs covered:** FR7, FR9, FR10, FR11, FR12, FR13, FR17, FR27 (узел пропал), FR28 (версия констант), FR36

### Epic 4: Оповещение и подтверждение
Полный Telegram (подписка по PIN, команды, подпись узла, пауза, «с опозданием»), Pushover для критичного с повтором до подтверждения, общее подтверждение во всех каналах, уведомления о перезагрузке и ежедневный отчёт.
**FRs covered:** FR14, FR15, FR16, FR25, FR26, FR28

### Epic 5: Настройка из локального веба
Веб-интерфейс на логических узлах поверх уже реплицируемого мягкого конфига: имена, зоны и граф зон, критичность, пороги, интервалы, приоритеты лидерства, подписчики, конфликты правок, экспорт/импорт, «забыть узел», временное выключение критичного правила.
**FRs covered:** FR23, FR24

### Epic 6: Обновление по воздуху, безопасный ввод и замена 1.x
OTA логических узлов (вместе с RCP H2) и коллекторов по Zigbee по одному с откатом, совместимость N/N−1, ввод по BLE, подписанные образы, secure boot и шифрование флеша только на рабочих узлах. Шлейфы с оконечными резисторами (ADS1115) — до монтажа, чтобы провода прокладывались один раз. Стенд остаётся постоянной тестовой сетью (отдельные ключи и Zigbee-сеть); выпуск идёт стенд → рабочая сеть. Завершается полной приёмкой по критерию успеха (с Pushover), параллельной работой с коробкой 1.x и её выводом. **Точка замены 1.x.**
**FRs covered:** FR2, FR30, FR31, FR32, FR35

### Epic 7: Датчики и их здоровье
Типизированные каналы с самоописанием, автообнаружение DS18B20/SHT/INA219/ADS1115 с появлением в вебе, контроль 12 В дымовиков и 220 В, события неисправности каналов.

### Epic 8: Правила и совместная логика

**Given** heartbeat

### Story 3.3: Доставка каждому живому логическому узлу

As a владелец,
I want, чтобы событие коллектора получил каждый живой логический узел,
So that оба считают одно и то же и ни один не пропускает тревогу.

**Acceptance Criteria:**

**Given** два живых логических узла
**When** коллектор отправляет событие
**Then** он повторяет каждому до его подтверждения

**Given** один логический узел объявлен мёртвым
**When** коллектор ждёт подтверждений
**Then** подтверждение этого узла больше не требуется

**Given** некритичное событие подтвердил хотя бы один логический узел
**When** подтвердили все живые или прошёл `GA_ACK_ALL_TIMEOUT`
**Then** событие удаляется из буфера коллектора

**Given** критичное событие
**When** его подтвердили все живые неглухие логические узлы, и не меньше двух, если неглухих два и больше

**Then** узел объявлен глухим: одно критичное событие здоровья «🔧 Узел «<имя>» не принимает события», узел исключён из ожидаемых
**And** первый ACK от него снимает глухоту

**Given** буфер коллектора переполнен
**When** приходит новое событие
**Then** вытесняются снимки, затем старейшие некритичные фронты
**And** неподтверждённое критичное не вытесняется; сверх `GA_COLLECTOR_CRIT_PER_CHANNEL` критичные фронты канала сливаются в первый, последний и счётчик

### Story 3.9: Аренда лидера в Telegram и конфликт 409

As a владелец,
I want, чтобы два узла, считающие себя лидерами, быстро договаривались через Telegram,
So that разрыв внутренней сети даёт максимум один-два дубля.

**Acceptance Criteria:**

**Given** узел стал `LEADER`
**When** он начинает работу с Telegram
**Then** он ведёт long polling `getUpdates` и продвигает `offset` (разбор команд появится в эпике 4)
**And** закрепляет в чате владельца сообщение-аренду `lease{node, priority, until}`
**And** продлевает его по периоду из `ga_config.h`

**Given** узел получил 409 на `getUpdates`
**When** он читает аренду через `getChat`
**Then** при свежей чужой аренде он переходит в `YIELDED` до её истечения
**And** при просроченной аренде забирает её

**Given** аренда недоступна
**When** получен 409
**Then** узел переходит в `YIELDED` на `base × (1 + ранг)`

**Given** узел в `YIELDED`
**When** есть что отправлять
**Then** он не делает `getUpdates` и не отправляет некритичное

**Given** сообщение-аренда
**When** оно закрепляется или продлевается
**Then** вторая строка — `<code>lease:1:<eui64>:<priority>:<until_epoch></code>`
**And** аренда с незнакомой версией формата считается просроченной

**Given** узел без доступной аренды
**When** он уходит в `YIELDED`
**Then** пауза = `GA_YIELD_BASE × (1 + ранг)`, ранг — позиция среди живых логических узлов по (`leader_priority`, EUI-64), с 0

**Given** `LEADER`
**When** до конца его аренды остаётся меньше `GA_LEASE_RENEW`
**Then** некритичное он не отправляет, критичное — отправляет

## Epic 10: Выходы и управление нагрузкой

Коллекторы с реле управляют нагрузкой по правилам, вручную из бота и веба и по командам MQTT; безопасные пределы держит сам узел с реле; реле работают без интернета и без лидера.

### Story 10.1: Канал-выход на коллекторе

As a владелец,
I want подключить к коллектору реле как канал-выход,
So that система может включать нагрузку и зуммер, а реле никогда не застревает включённым.

**Acceptance Criteria:**

**Given** манифест коллектора с выходом `switch` или `buzzer` (пин, необязательный вход подтверждения)
**When** узел стартует
**Then** выход описывается как канал `output` тем же самоописанием, что и датчики (7.1)
**And** до первой команды выход в безопасном состоянии из конфига: `off` или `hold`

**Given** безопасное состояние
**When** его задают
**Then** допустимы только `off` и `hold`, `on` отвергается при сохранении
**And** `hold` хранится в NVS в пределах `GA_COLLECTOR_NVS_BUDGET`

**Given** выход включён
**When** проходит `max_on` (мягкий, ≤ `GA_OUTPUT_MAX_ON_MAX`) или предел зуммера `GA_BUZZER_MAX`
**Then** узел выключает его сам, без сети, и публикует `output_state` с причиной

**Given** нет heartbeat ни одного логического узла дольше `GA_OUTPUT_LINK_LOST`
**When** узел это обнаруживает
**Then** выход переходит в безопасное состояние
**And** локальные правила (10.5) продолжают работать

**Given** вход подтверждения (вторая пара контактов)
**When** его состояние не совпало с командой за `GA_OUTPUT_FEEDBACK_TIMEOUT`
**Then** канал переходит в `health = fault` и создаётся событие здоровья

**Given** катушка 24 В
**When** собирается стенд
**Then** реле включается через ключ (транзистор с диодом или ULN2003) от отдельного питания 24 В, схема — в `sensor-catalog.md`

### Story 10.2: Арбитраж и команды выходов

As a владелец,
I want, чтобы реле всегда слушалось самой важной и самой свежей команды,
So that дубли, порядок прихода и отказ любого логического узла не меняют итог.

**Acceptance Criteria:**

**Given** узел выхода
**When** приходит `output_cmd{cmd_id, channel_id, level, value, ts, until}`
**Then** команда (включая `release`) занимает слот своего уровня, только если её пара (HLC `ts`, `cmd_id`) больше пары слота
**And** действует старший слот со значением `protect > manual > auto`, без них выход выключен
**And** очищенный, истёкший или отсечённый `max_on` слот хранит `ts`, команда не новее его отклоняется с причиной `stale`

**Given** повтор команды с той же парой (`cmd_id`, `level`)
**When** он приходит
**Then** он подтверждается и не применяется повторно
**And** тот же `cmd_id` с более высоким уровнем принимается как повышение и очищает нижний слот

**Given** отклонение `stale`
**When** значение совпадает с действующим или команда пришла от правила
**Then** пользователю отказ не показывается, только запись в журнал

**Given** слот `protect`
**When** коллектор перезагружается или теряет связь дольше `GA_OUTPUT_LINK_LOST`
**Then** слот `protect` (записанный в NVS до ACK из резерва `GA_OUTPUT_NVS_RESERVE`) восстанавливается с остатком `max_on`/`until`, безопасное состояние действует только на `manual` и `auto`
**And** логические узлы, увидев новый `boot` коллектора, шлют последнюю известную команду каждого слота, включая `release` и `off`
**And** `GA_OUTPUT_BOOT_LOOP` перезагрузок подряд во включённом состоянии дают безопасное состояние и `fault`; счётчик хранится в NVS и сбрасывается после `GA_OUTPUT_BOOT_STABLE` непрерывной работы

**Given** `max_on` или `GA_BUZZER_MAX`
**When** выход включён и приходят новые команды `on`
**Then** отсчёт идёт от перехода в `on` и не перезапускается

**Given** изменилось действующее состояние или команда отвергнута
**When** узел это обрабатывает
**Then** публикуется `output_state{value, level, cmd_id, feedback}` или событие отказа с причиной

**Given** логические узлы
**When** у них есть команда для выхода
**Then** каждый шлёт её сам адресным надёжным сообщением классом `critical`, без лидера, с повтором до ACK
**And** коллектору без этого выхода в описании каналов (узел N−1) команда не отправляется

**Given** детерминированный симулятор (2.7)
**When** команды приходят в любом порядке, с дублями, при отказе любого логического узла
**Then** итоговое состояние выхода одинаково, в том числе при расходящихся часах логических узлов
**And** `manual` не перебивает `protect`, `max_on` срабатывает без сети
**And** `on` с `dur_s` = 10, перезагрузка коллектора через 20 с → выход остаётся выключенным; `pulse` без длительности отклоняется

### Story 10.3: Действие правил «установить выход»

As a владелец,
I want, чтобы правило включало реле или зуммер,
So that, например, протечка сразу включает зуммер, а движение в «охране» — свет.

**Acceptance Criteria:**

**Given** правило с действием «установить выход» (вкл, выкл, импульс зуммера)
**When** оно срабатывает
**Then** команда несёт `cmd_id = rule_id@event_id` причины и `ts` причины (у оконного правила — производное событие и `window_start`), одинаковые на всех логических узлах
**And** уровень — `protect`, если итоговое `k` причины критично, иначе `auto`

**Given** узел перезагрузился и проходит журнал (AD-16)
**When** события до курсора `Rules` обрабатываются
**Then** команды выходов не выдаются

**Given** причина старше `GA_CMD_MAX_AGE` (событие доставлено поздно)
**When** правило срабатывает
**Then** включающие команды не выдаются, а `release` и `off` выдаются всегда

**Given** правило тревоги с действием выхода
**When** канал срабатывает повторно в открытом эпизоде (AD-21)
**Then** новая команда не выдаётся, действие срабатывает на открытие эпизода

**Given** режим действия «пока активно», «до подтверждения» или «импульс»
**When** канал возвращается в норму, тревогу подтверждают «Принято» или проходит импульс
**Then** правило выдаёт `release` по своему режиму всем слотам, занятым его командами, и выход освобождается
**And** `release` по `ack` несёт `ts` = max(`ts` подтверждения, `ts` включившей команды) + 1

**Given** редактор правил (8.8)
**When** выбирается действие
**Then** доступны выходы с их подтипами

### Story 10.4: Ручное управление из веба и бота

As a владелец или оператор,
I want включать и выключать реле вручную,
So that могу управлять нагрузкой без правил.

**Acceptance Criteria:**

**Given** веб (после входа) или бот (владелец и операторы, выход с `bot_control`)
**When** нажата кнопка «вкл», «выкл» или «авто»
**Then** принявший узел создаёт реплицируемое событие `output_intent` уровня `manual` с HLC `ts` не меньше последнего известного ему `output_intent`/`output_state` этого выхода
**And** шлёт команду сразу после записи в FRAM, остальные логические узлы — по приходу события

**Given** часы узлов расходятся
**When** пользователь включает выход из веба одного узла и выключает из бота другого
**Then** действует последняя по смыслу команда либо пользователь видит отказ `stale`, молчаливой потери нет

**Given** выход держит `protect`
**When** приходит ручная команда
**Then** пользователь видит отказ с причиной, например «защита держит: протечка подвала»

**Given** «авто»
**When** оно выбрано
**Then** уходит `release` уровня `manual`, и выход возвращается правилам

**Given** экраны «Выходы» в вебе и боте
**When** они открыты
**Then** видны состояние, уровень, кто включил, `max_on` и подтверждение, по UX-DR из `bmad-ux`

### Story 10.5: Локальные правила на коллекторе

As a владелец,
I want, чтобы простое правило «протечка → зуммер» работало на самом коллекторе,
So that защита срабатывает даже при выключенных логических узлах.

**Acceptance Criteria:**

**Given** правило одного события канала коллектора с действием на выход того же коллектора, без окна и `when`
**When** оно сохраняется
**Then** `Config` помечает его локальным, и в вебе оно отмечено «локально на <узел>»

**Given** набор локальных правил коллектора
**When** он меняется
**Then** коллектор получает таблицу адресным надёжным сообщением с версией (≤ `GA_LOCAL_RULES_MAX`), хранит её через `Storage`
**And** сообщает версию в heartbeat, расхождение видно в вебе

**Given** все логические узлы выключены
**When** срабатывает вход локального правила
**Then** коллектор сам выдаёт команду на свой выход

**Given** логические узлы работают
**When** они исполняют то же правило
**Then** их команда несёт тот же `cmd_id` и `ts`, и узел выхода применяет её один раз

**Given** новая версия таблицы приходит частями
**When** пришли не все части или узел перезагрузился
**Then** действует прежняя таблица
**And** полная версия пишется в неактивную копию A/B и включается одной записью

### Story 10.6: Входящий MQTT

As a владелец,
I want управлять реле из Home Assistant или Node-RED через MQTT,
So that внешняя автоматизация работает вместе с системой.

**Acceptance Criteria:**

**Given** выход с флагом `mqtt_control`
**When** на `<prefix>/<node>/<channel>/set` приходит `{value, until?, ts?}`
**Then** MQTT-узел записывает `output_intent` в FRAM и только затем отправляет PUBACK

**Given** команда с полем `id`
**When** её получают MQTT-узел и ведомый и оба создают намерение
**Then** у обоих намерений один `cmd_id` (SHA-256 от темы и `id`), и реле применяет команду один раз

**Given** две одинаковые команды «вкл» подряд без `id`
**When** они приходят
**Then** обе обрабатываются как разные команды, отпечаток не склеивает их

**Given** выход без `mqtt_control`, retained-сообщение или `ts` старше `GA_CMD_MAX_AGE`
**When** приходит команда
**Then** она отбрасывается, причина публикуется в `<prefix>/<node>/<channel>/result`

**Given** все логические узлы с логином MQTT
**When** они подключаются
**Then** подписываются на темы `set` (QoS 1) по MQTT 5 постоянной сессией с Client ID `ga2-<EUI-64>` (`clean_start = false`, session expiry `GA_MQTT_SESSION_EXPIRY` ≥ `GA_CMD_MAX_AGE`)
**And** брокер без MQTT 5 или урезанный срок сессии — событие здоровья, `mqtt_control` на этом узле недоступен

**Given** MQTT-узел отказал после приёма команды
**When** за `GA_MQTT_INSURE_T` после приёма ведомому не стало известно ни одного намерения `manual` этого выхода
**Then** ведомый создаёт намерение сам с HLC `ts` своего приёма и отпечатком сообщения (хеш темы и payload)
**And** ведомый отправляет PUBACK только после записи страховочной записи во FRAM; после его перезагрузки команда восстанавливается из записи
**And** не создаёт, если намерение с этим отпечатком уже есть
**And** симулятор проверяет: принятая команда доходит до реле при отказе MQTT-узла

**Given** команда исполнена
**When** меняется состояние выхода
**Then** `state` выхода публикуется retained с подтверждённым значением
