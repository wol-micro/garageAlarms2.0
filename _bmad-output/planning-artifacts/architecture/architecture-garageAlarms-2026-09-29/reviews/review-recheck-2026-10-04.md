# Повторная проверка spine после правок 2026-10-04

Мерило: **не потерять событие > не флудить > остальное.** Дубль допустим, потеря — нет.
Spine не правился; предложения — входные данные для `.memlog.md`.

## Вердикт

Правки закрыли большую часть S1 прошлого обзора: два счётчика `seq` и `lw`, порядок «факт → производное»,
виды регионов, миграция по суперблоку, `boot_ready`, две очереди `Storage`, курсоры потребителей журнала,
исходящая очередь без обратного давления. Новые формулировки при этом недоопределены в трёх местах, и
каждое даёт сценарий, где все AD соблюдены, а событие потеряно:

1. **Один надёжный счётчик на узел при адресных надёжных сообщениях** (синхронизация конфига одному пиру,
   параметры одному коллектору) по-прежнему даёт получателю дыры, которые `lw` не закрывает, пока
   отправитель держит сообщения для другого адресата (остаток A1/C1).
2. **`lw` обрезает anti-entropy.** Сводка «не ниже `lw`» плюс отсутствие правила, когда отправитель вправе
   поднять `lw`, оставляет логический узел без события, которое коллектор уже выпустил из буфера.
3. **«Все живые неглухие» может стать пустым множеством.** Если глухими объявлены все логические узлы,
   условие выпуска критичного выполняется при нуле ACK. Выхода из глухоты в spine нет.
4. **Эпизод тревоги** (AD-21) без верхней границы длительности и без правила для mute и `ack`
   превращает новое вторжение в правку старого сообщения, а закрытие эпизода по локальному `now`
   и ключ по «первому пришедшему» срабатыванию расходятся между узлами.

## 2. Новые дыры, внесённые правками

### Н1 (S1). Адресные надёжные сообщения в общем надёжном счётчике: окно получателя встаёт, `lw` не спасает

- **Пара:** `Delivery` логического узла L1 (AD-7: надёжный счётчик один на узел и включает «события,
  `ack`, `delivered`, конфиг») × `Delivery` получателя L2 или коллектора C2 (AD-17: база = max(префикс, `lw`)).
- **Сценарий.** L1 синхронизирует конфиг с вернувшимся L3 (AD-14, `bulk`, сотни надёжных сообщений
  адресно L3) или шлёт параметры каналов коллектору C1 (AD-14, надёжное сообщение с версией). Номера этих
  сообщений L2 и C2 не получат никогда — для них это дыры. `lw` по определению — «наименьший `seq`,
  который отправитель ещё хранит», а L1 хранит сообщения для L3/C1 до их ACK. Если L3 медленный или C1
  недоступен, но жив по heartbeat (тот же «глухой» случай), `lw` стоит, а следующие надёжные кадры L1
  уходят за `GA_SEQ_WINDOW` у L2. L2 перестаёт подтверждать `ack`, `delivered` и события собственных
  датчиков L1. Страховка AD-11 у L2 ломается: он не видит `delivered` и отправляет повторно (флуд), а
  события датчиков L1 расходятся между узлами (AD-16).
- **Исправление (AD-5 + AD-7 + AD-17).** Развести идентичность события и антиповтор канала:
  > ID события `(node, boot, seq)` в `body` нумерует только события (широковещательный поток, одинаковый для
  > всех получателей своего класса). Адресные надёжные сообщения (синхронизация конфига, параметры коллектора,
  > ответы anti-entropy) нумеруются отдельным счётчиком на пару `(src, dst)`. `lw` в кадре относится к тому
  > потоку, к которому принадлежит кадр.
  Тест симулятора: «адресная синхронизация с медленным пиром не останавливает приём у третьего узла».

### Н2 (S1). `lw` обрезает anti-entropy: событие, выпущенное коллектором, не доходит до отставшего узла

- **Пара:** `Delivery` коллектора (AD-8: некритичное покидает буфер после одного ACK и `GA_ACK_ALL_TIMEOUT`;
  критичное — после ACK всех **неглухих**) × anti-entropy между логическими узлами (AD-8: сводка
  «`(node, boot)` → принятые `seq`» **не ниже `lw`**).
- **Сценарий.** L1 подтвердил событие `(C, 5, 300)`, L2 пропустил его (разрыв, глухота). Коллектор выпускает
  событие и, по смыслу `lw`, поднимает `lw` выше 300. Сводка L1 по `(C, 5)` теперь начинается с `lw` > 300;
  L2 не видит у L1 номера 300 и не запрашивает его, его окно по AD-17 уже сдвинуто через 300 по `lw`.
  У L2 события нет навсегда. Это прямое расхождение входов AD-16. Для критичного это значит: L2 был
  объявлен глухим, L1 подтвердил, L1 потом сгорел — L2, ставший `LEADER`, о тревоге не знает, а
  «принимает отправку всех недоставленных элементов» (AD-10) не помогает: элемента у него нет.
- **Чего нет в spine.** Правила, когда отправитель вправе поднять `lw`. Сейчас ничто не запрещает поднять
  его над неподтверждённым критичным.
- **Исправление (AD-8 + AD-17):**
  > `lw` источника ограничивает только окно антиповтора от этого источника. Отправитель поднимает `lw` над
  > сообщением только после его ACK хотя бы одним логическим узлом или после вытеснения некритичного по
  > AD-8. Сводка anti-entropy между логическими узлами ограничена глубиной журнала держателя, а не `lw`
  > источника: пир, у которого событие есть, предлагает его, пока оно в журнале. Узел, вышедший из глухоты,
  > получает всё пропущенное через anti-entropy.

### Н3 (S1). «Все живые неглухие» = пустое множество: критичное выпускается без единого ACK; выхода из глухоты нет

- **Пара:** `Delivery` коллектора (AD-8: глухой — жив по heartbeat, но не подтверждает дольше
  `GA_ACK_ALL_TIMEOUT`; критичное выпускается, когда подтвердили все неглухие, и не меньше двух, если неглухих
  ≥ 2) × Zigbee-mesh под нагрузкой.
- **Сценарий ложной глухоты.** Heartbeat логического узла — широковещательный и доходит flooding'ом, а ACK —
  юникаст по маршруту; маршрут к коллектору сломан или перегружен (шторм от дребезга, OTA коллектора, `bulk`
  по Zigbee при упавшем WiFi). Плюс конвенция «повтор с экспоненциальной паузой»: к концу
  `GA_ACK_ALL_TIMEOUT` у узла было лишь 2–3 шанса ответить. Под общей перегрузкой глухими становятся **все**
  логические узлы. Условие «подтвердили все неглухие» выполняется пустым множеством, «не меньше двух» не
  действует (неглухих меньше двух), и критичное покидает буфер с нулём ACK — **потеря**.
- **Дополнительно.** (а) Выход из глухоты не определён: одна реализация снимает её по первому ACK, другая —
  никогда; при «никогда» глухота накапливается до пустого множества даже без общей перегрузки.
  (б) «Критичное событие здоровья» о глухоте шлёт каждый коллектор про каждый узел; при мигании это поток
  Pushover `priority=2` (флуд), эпизод AD-21 его не схлопывает — он определён для каналов.
  (в) При исчерпании `GA_COLLECTOR_CRIT_RESERVE` (мигающий критичный PIR, логические узлы недоступны) поведение не
  определено — следующее критичное другого канала некуда положить.
- **Исправление (AD-8):**
  > Критичное покидает буфер коллектора только после ACK хотя бы одного логического узла — всегда, и не меньше
  > двух, если неглухих ≥ 2. Глухота объявляется не раньше, чем узлу отправлено ≥ `GA_DEAF_MIN_RETRIES` повторов
  > за `GA_ACK_ALL_TIMEOUT`, и снимается первым ACK. Событие здоровья «глухой» — одно на `(collector, node)` в
  > эпизоде, с гистерезисом. Критичные фронты одного канала сверх `GA_COLLECTOR_CRIT_PER_CHANNEL` сливаются на
  > коллекторе в запись «первый + последний + счётчик», чтобы резерв не съедал один мигающий канал.

### Н4 (HIGH, на грани S1). Эпизод тревоги глотает новое вторжение; эпизоды расходятся между узлами

Правило AD-21: эпизод закрывается, когда канал в норме и продержался в ней `GA_ALARM_REARM`; повторные
срабатывания в открытом эпизоде только правят сообщение, в том числе после `ack`.

- **Проглатывание.**
  1. *После `ack`.* PIR в гараже мигает от кота или занавески, нормы дольше `GA_ALARM_REARM` нет. Владелец
     подтвердил. Через 3 часа реальное вторжение на том же канале — это «повторное срабатывание» открытого
     эпизода: правка старого сообщения далеко вверху чата, без Pushover. Событие формально сохранено,
     человек его не увидел.
  2. *Обрыв или неисправность.* Нарушитель режет провод: канал в `open`/`short`, «нормы» нет, эпизод не
     закрывается. Восстановление и последующее срабатывание снова попадают в старый эпизод. Из текста не
     ясно, считается ли `health ≠ ok` нормой.
  3. *Mute некритичного.* Первое срабатывание пришлось на окно mute — сообщение не отправлено. После
     окончания mute новые срабатывания только «правят» сообщение, которого нет. Одна реализация молчит (потеря
     уведомления), другая отправляет (расхождение).
  4. *Напоминание о дыме* (`rule-templates.md`, шаблон 1, каждые 15 мин) и «`ack` гасит повторы во всех
     каналах»: не сказано, гасит ли `ack` напоминания длящейся тревоги. Две реализации разойдутся.
- **Недетерминированность.**
  1. *Закрытие по локальному `now`.* «Продержалась `GA_ALARM_REARM`» решается по тику узла. Срабатывание с
     `ts` внутри интервала, опоздавшее к L2, у L1 попадает в эпизод, а у L2 эпизод уже закрыт, и оно
     открывает новый: новая тревога и Pushover у одного узла и правка у другого. После смены лидера
     получится второй Pushover на тот же эпизод.
  2. *Ключ по «первому срабатыванию».* Если раньше пришло более позднее срабатывание (а раннее
     задержалось в буфере коллектора или в anti-entropy), `event_id` первого у узлов разный. Ключи
     эпизода разные, и `Notify` их не склеит — его идемпотентность по `event_id`.
  3. *Перестроение после перезагрузки.* Эпизод может длиться дольше `GA_RULE_WINDOW_MAX`, а журнал
     вытесняет обработанное старше окна. Проход от курсора `Rules` не видит первого срабатывания: эпизод
     неизвестен, и следующее срабатывание открывает новый эпизод с новым ключом. Это дубль-тревога у
     перезагрузившегося узла и расхождение с остальными.
  4. *Поздние события.* Горизонт AD-16 не говорит, как поздняя базовая тревога критичного канала
     соотносится с эпизодами: открывает новый эпизод, сливается с закрытым или переключает ключ открытого.
  5. *Правка после смены лидера.* Чтобы править сообщение, новому лидеру нужен `message_id` отправленной
     тревоги. Ни `delivered`, ни регион `Notify` его не реплицируют, так что одна реализация правку
     пропустит, другая отправит новое сообщение.
- **Исправление (AD-21 + AD-16):**
  > Эпизод вычисляется только по `ts` источника: закрыт, если нет срабатывания с `ts` в
  > `[ts_нормы, ts_нормы + GA_ALARM_REARM]`; решение о закрытии принимается не раньше
  > `ts_нормы + GA_ALARM_REARM + GA_EPISODE_GRACE`. Ключ — `(channel_id, ts первого срабатывания)`, где «первое»
  > определяется по `ts`, а не по приходу. Открытие эпизода `Rules` публикует производным событием через
  > `Delivery` (реплицируется, переживает вытеснение журнала и перезагрузку). Норма = неактивное значение и
  > `health = ok`. Срабатывание позже `ack` + `GA_ALARM_REARM` или позже начала эпизода + `GA_EPISODE_MAX`
  > — новая тревога (с Pushover для критичного). Если первое срабатывание эпизода заглушено mute, первое
  > срабатывание после окончания mute отправляется как тревога. Поздние события за горизонтом эпизоды не
  > меняют — это отдельная тревога «с опозданием». `delivered` несёт `message_id` по единице доставки;
  > если правка невозможна, отправляется новое сообщение. Явно сказать, гасит ли `ack` напоминания шаблона 1.

### Н5 (MEDIUM). `offset = −1` новым узлом стирает чужие необработанные обновления

- **Пара:** `Notify` вновь включённого (или переформатированного) узла (AD-10: без состояния от пиров —
  `offset = −1`) × `Membership` (AD-9: «узел без пиров, но с uplink — `LEADER`»).
- **Сценарий.** В первые секунды после старта узел ещё не получил heartbeat пиров и по AD-9 считает себя
  `LEADER`. Он вызывает `getUpdates` с `offset = −1`. Отрицательный `offset` в Telegram подтверждает
  (забывает) все более ранние обновления. Нажатое владельцем «Подтвердить», `/mute` или подтверждение
  опасной команды, ещё не забранные настоящим лидером, исчезают. Повторы критичного продолжаются (флуд),
  команда потеряна. Затем 409 и `YIELDED` — уже после ущерба.
- **Исправление (AD-9 + AD-10):**
  > После старта узел не становится `LEADER` и не вызывает `getUpdates` раньше `GA_JOIN_GRACE`
  > (≥ 3 периодов heartbeat), пока не получит heartbeat пиров или не истечёт этот срок.
  > `offset = −1` допустим, только если за `GA_JOIN_GRACE` не услышан ни один пир и аренда в
  > `getChat.pinned_message` просрочена или отсутствует.

### Прочие новые замечания (S3 / LOW)

- **Н6 (S3). Повышение критичности на логическом узле недетерминировано.** AD-14 разрешает логическому узлу
  поднять `k`, пока версия параметров коллектора расходится. Но L1 и L2 могут иметь разные версии конфига:
  один повышает, другой нет, и правила считаются по разной критичности. Исправление: повышенная критичность
  определяется по версии конфига, записанной в событие при приёме первым узлом, или по максимуму `k` среди
  узлов (повышение монотонно, реплицировать как «`k` ≥ X»).
- **Н7 (S3). Курсор `Config` в журнале.** AD-28 называет `Config` потребителем журнала, но не говорит, что
  именно он потребляет. Если это записи синхронизации конфига, то при уплотнении конфига и общей
  синхронизации «забрать у соседа» неясно, сдвигается ли курсор. Уточнить одной строкой.
- **Н8 (LOW). Команды правил в `Sensor`.** AD-16: «команды правил (опросить, burst-интервал)». В диаграмме
  нет стрелки `Rules → Sensor`, а между `Delivery` и `Sensor` стрелка идёт только `Sensor → Delivery`.
  Путь допустим только как событие по подписке от `Delivery` (команда — надёжное сообщение с TTL). Его надо
  назвать, иначе кто-то добавит прямой вызов.

### Константы

Названы в spine (14): `GA_ACK_ALL_TIMEOUT`, `GA_ALARM_REARM`, `GA_CMD_MAX_AGE`, `GA_COLLECTOR_CRIT_RESERVE`,
`GA_CONFIG_VERSION`, `GA_DEDUP_BOOTS`, `GA_FLASH_OP_MAX_MS`, `GA_OUTBOX_CRIT_QUOTA`, `GA_RULE_WINDOW_MAX`,
`GA_SEQ_WINDOW`, `GA_STORAGE_CHUNK`, `GA_TG_EXECUTED_IDS`, `GA_TICK_JITTER`, `GA_TOMBSTONE_TTL`.
**Ни одной из них нет в `tunables.md`** (L5 открыт; AD-25 формально не выполнен).

Величины, которые в правилах есть, но имени не получили:
- переходный период `kid` (AD-5) — нужен `GA_KID_TRANSITION`, и он должен быть конечным (см. A14);
- T «~45 с» (AD-11), «15 мин» возврата лидерства (AD-9), N/M гистерезиса uplink, `base` для `YIELDED` (AD-10),
  «≤ N ч» выключения критичного правила (AD-22), «30 мин» пакета ключей (AD-23): в `tunables.md` значения
  есть, имён `GA_*` нет;
- запас идемпотентности `Notify` («`GA_RULE_WINDOW_MAX` с запасом», AD-21) — без имени, две реализации
  выберут разный запас;
- бюджет износа NVS коллектора (A4) — без имени;
- `GA_JOURNAL_RATE_BUDGET` из прошлого обзора в правило не вошёл.

Предлагаемые новые (из этой проверки): `GA_DEAF_MIN_RETRIES`, `GA_COLLECTOR_CRIT_PER_CHANNEL`, `GA_EPISODE_GRACE`,
`GA_EPISODE_MAX`, `GA_JOIN_GRACE`, `GA_KID_TRANSITION`.

### Состав heartbeat (AD-19) отстал от новых правил

Новые AD опираются на поля heartbeat, которых нет в перечне AD-19: водяной знак конфига `W` (AD-14), версия
параметров каналов коллектора (AD-14), `lw` по незакрытым загрузкам (AD-17), `GA_CONFIG_VERSION` (AD-25,
упомянут только там). Перечень AD-19 нужно сделать полным, иначе две реализации heartbeat не стыкуются.

## 4. Инварианты симулятора, которые стоит добавить (AD-27, уровень 2)

1. Адресная синхронизация конфига с медленным или глухим пиром не останавливает приём у третьего узла (Н1).
2. Событие, подтверждённое одним логическим узлом и выпущенное коллектором, через ограниченное время есть
   у каждого живого логического узла (Н2).
3. Критичное никогда не покидает буфер коллектора без ACK хотя бы одного логического узла, в том числе при
   глухоте всех (Н3).
4. Срабатывание после `ack` + `GA_ALARM_REARM` всегда даёт новую тревогу; ключи эпизодов совпадают у всех
   логических узлов при любом порядке прихода и после перезагрузки (Н4).
5. Старт нового узла не теряет обновлений Telegram, которые не забрал действующий лидер (Н5).
