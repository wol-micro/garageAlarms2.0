# Сверка spine с входами — garageAlarms 2.0

**Дата:** 2026-09-29
**Spine:** `ARCHITECTURE-SPINE.md` (draft)
**Входы:** `forge/garage-device-network/{forged-idea.md,.memlog.md}`, `forge/rules-config-model/{forged-idea.md,.memlog.md}`, `.memlog.md` архитектуры, легаси-код garageAlarms 1.x (`CLAUDE.md`, `*.ino/*.cpp/*.h`).
**Правило сверки:** проверялись только решения и ограничения. Если в памятке архитектуры принято более позднее решение, оно считается приоритетным (коллекторы только Zigbee, CBOR вместо JSON, ID узла = EUI-64, `(node, boot, seq)`, приоритет лидера, C5/H2, ESP-IDF, новый репозиторий). Такие случаи не отмечаются.

## Вердикт

Сетевое ядро spine (AP-модель, лидерство, арбитраж Telegram, at-least-once, идентичность, классы трафика, уровни конфига) переносит входы точно. Не попали в spine в основном решения о внешнем канале и пользователе: Pushover как канал тревоги с подтверждением, подписчики и владелец, ограничения Telegram-управления, политика переполнения очереди. Кроме того, одна конвенция (критичность решается функцией в `proto`) противоречит модели forge, где критичность задаётся атрибутом канала или правила.

## Находки

Важность: **H** — нарушает приоритет «не потерять > не флудить» или затрагивает границу между узлами; **M** — решение из входа не записано, реализации разойдутся; **L** — уточнение.

### H-1. Pushover: только критичное, emergency с подтверждением, «подтверждение гасит повторы везде»
- **Источник:** rules-config-model/forged-idea.md, раздел «Управление и каналы» и «Открыто»; memlog L23–25: второй канал = канал тревоги (только критичные, priority=2, повтор до подтверждения); подтверждение в любом канале = событие «принято» в gossip, которое гасит повторы и в Telegram; лишнюю экстренную тревогу после переключения лидера отменять через cancel receipt.
- **Spine:** Pushover упоминается только в `Notify` и в AD-10 (receipts реплицируются). Нет ограничения «только критичное», нет emergency-режима, нет события «принято», нет гашения повторов между каналами, нет cancel по receipt.
- **Исправление:** добавить в AD-10/AD-11 (или отдельным AD): «Pushover получает только критичные события, priority=2. Подтверждение в любом канале порождает реплицируемое событие `ack{event_id}` (тип в `proto`), которое останавливает повторы во всех каналах. Лишнюю emergency-тревогу, возникшую при переключении лидера, отменять по receipt».

### H-2. Подписчики, владелец и авторизация Telegram отсутствуют
- **Источник:** легаси (`Store.cpp`, `BotUI.cpp`): подписка по PIN, владелец всегда подписан и не может отписаться, уведомления о перезагрузке идут только владельцу. rules-config memlog L18: авторизация по `chat_id`, утечку токена выдаёт тот же 409.
- **Spine:** в S-конфиге (AD-14) нет списка подписчиков и владельца. Не сказано, чем реплицируется состояние подписки и mute (`Config` или `Notify`). Новый лидер может не знать получателей. Конвенция «только владельцу» ссылается на владельца, которого модель не определяет.
- **Исправление:** в AD-14 добавить в S «подписчики (chat_id), владелец, окно mute, маршрутизация по получателям». Записать: владелец задаётся при provisioning и не может отписаться; подписка через `/subscribe` с кодом; команды принимаются только от подписанных `chat_id`.

### H-3. Политика переполнения очередей и отказа от повторов
- **Источник:** легаси `Notifier.cpp`: при заполнении очереди сначала вытесняется самый старый некритичный элемент. Коллектор по forge держит «маленький постоянный буфер до e2e ACK».
- **Spine:** AD-8 и AD-4 требуют хранить событие до ACK, но не говорят, что делать, когда буфер коллектора или исходящая очередь логического узла заполнены. Не сказано и о лимите попыток: в легаси через 12 попыток элемент выбрасывается, что для критичного при приоритете «потеря — нет» недопустимо.
- **Исправление:** добавить правило в AD-8: «При переполнении вытесняется самый старый некритичный элемент. Критичный вытесняется только другим критичным, и каждое вытеснение — событие здоровья. Критичное не снимается по счётчику попыток, только по `delivered`».

### H-4. Критичность: конвенция противоречит модели forge
- **Источник:** rules-config-model: в описании канала есть поле `criticality`, в экземпляре правила — `severity` и `notify` (это S-конфиг). Критичные правила, например дым и вода, определяются конфигом.
- **Spine:** в Consistency Conventions записано «Только `Events.isCritical`-подобная функция в `proto` решает, что критично». Это статическое решение по типу сообщения, а модель forge настраиваемая. Памятка архитектуры замену не обосновывает.
- **Исправление:** переформулировать: «Критичность события = `severity` правила или `criticality` канала из S-конфига. `proto` задаёт только класс трафика `critical` и единую функцию выбора, а не список типов». Уточнить AD-19 («для критичных каналов») ссылкой на это поле.

### M-1. Выключение критичного правила — только из локального веба
- **Источник:** rules-config memlog L44 (lock): «выключаются только из локального веба и только временно».
- **Spine:** AD-14 сохраняет «только временно (≤ N ч)» и «событие всем», но теряет «только из локального веба». Поскольку Telegram может выполнять ограниченный набор команд, такое выключение формально становится доступным через Telegram.
- **Исправление:** в AD-14 написать «Критичное правило выключается только из локального веба, только временно…». Набор команд Telegram перечислить: статус, отчёты, подтверждение, некритичные действия.

### M-2. Команды с ID и TTL, автоматический откат временных изменений
- **Источник:** rules-config/forged-idea.md, раздел «Правила»: «Команды — с ID и TTL; временные изменения откатываются сами» (burst-интервал, опрос сейчас).
- **Spine:** есть только идемпотентность Telegram-команд по `update_id` (AD-10). Внутренние команды (к коллектору, между логическими узлами) не имеют ID и TTL. Откат временных изменений не описан, хотя это межузловой контракт.
- **Исправление:** добавить в AD-5/AD-16: «Команда = `{cmd_id, ttl}` в `proto`. Временное изменение S хранит срок и откатывается само на всех логических узлах. Просроченная команда отбрасывается».

### M-3. Схема экземпляра правила и самоописания канала не закреплена
- **Источник:** rules-config: экземпляр `{id, type, enabled, params, set, severity, notify, ver}`; описание канала `{node, channel, kind, name, zone, purpose, criticality, unit, cfg_ver}`; состояние `{state, value, health, ts, seq}`; обмен сводками версий (anti-entropy).
- **Spine:** AD-15/AD-16 говорят, что такие объекты есть, но не перечисляют поля. Эти объекты реплицируются между узлами, значит, пересекают границу, а не относятся к деталям движка из Deferred.
- **Исправление:** перечислить обязательные поля в AD-15/AD-16 (или указать «определены в `proto`») и явно назвать anti-entropy по сводкам версий механизмом синхронизации S.

### M-4. Конфликт LWW показывать в вебе
- **Источник:** garage-device-network/forged-idea.md, раздел «Открытые трещины» и memlog L55: LWW молча теряет конкурентную правку, это тоже потеря данных, поэтому конфликт показывать в вебе.
- **Spine:** в AD-14 описано слияние LWW по HLC, но проигравшая правка не сохраняется и не показывается.
- **Исправление:** в AD-14 добавить: «При слиянии с конкурентной правкой проигравшее значение сохраняется как конфликт и показывается в `Ui`, пока его не разрешат».

### M-5. Прозрачность в чате: подпись узла и `/status` с лидером
- **Источник:** garage-device-network: «В чате: подпись узла, `/status` с лидером, `/leader <узел>`»; memlog L59, L62.
- **Spine:** есть только `/leader` (AD-9). Нет подписи узла-отправителя в сообщениях, нет лидера и статусов узлов в `/status`. Нет пометки о причине отправки: ведомый по страховке, `ISOLATED` («аварийный режим» есть в AD-11).
- **Исправление:** в AD-10 добавить: «Каждое внешнее сообщение подписано именем узла-отправителя; `/status` показывает лидера и статус каждого логического узла».

### M-6. Уроки поведения легаси, не перенесённые явно
Эти решения из 1.x служат приоритету «не потерять / не флудить» и не заменены памяткой архитектуры:
- **Антидребезг по времени плюс cooldown, прогрев только для PIR.** Spine пишет только «антидребезг». Нужно записать: уровень должен удерживаться непрерывно *_DEBOUNCE_MS (защёлка по одному отсчёту запрещена); после срабатывания cooldown на канал; период прогрева допустим только для некритичных каналов, у дыма его нет.
- **Метка «доставлено с опозданием».** Если событие ушло наружу позже порога (в легаси 120 с), текст показывает исходное время и помечается как опоздавшее. В распределённой схеме, при досылке ведомым или после изоляции, это ещё важнее. Добавить в AD-10 или в конвенции.
- **Ежедневный heartbeat пользователю** (`HEARTBEAT_HOUR`), чтобы молчание что-то значило. AD-19 описывает только межузловой heartbeat. Добавить в конвенцию «Защита от флуда/живость»: одно ежедневное сообщение от лидера.
- **Причина сброса (`esp_reset_reason`)** в уведомлении о перезагрузке и в `/status`. Добавить в конвенцию об уведомлениях о перезагрузке.
- **«Мёртвая связь → перезагрузка».** В легаси узел перезагружается при WiFi down > 10 мин или Telegram недоступен > 30 мин. В spine политики самоперезагрузки нет. Решить явно: оставить для `Sys` с учётом того, что у `FOLLOWER` нет Telegram, или отказаться.
- **TLS только после синхронизации часов.** AD-20 допускает лидера как источник времени без NTP, но лидеру для TLS самому нужно реальное время. Записать: `Notify` не открывает TLS до получения валидного времени.
- **Темп отправки в Telegram** (минимальный интервал между отправками, `NOTIFY_MIN_SEND_GAP_MS`). В AD-10 сейчас ничего нет. Добавить: пауза между отправками и учёт 429 `retry_after`.

### L-1. Оконечные резисторы (EOL) + АЦП на проводных шлейфах
- **Источник:** garage-device-network: «Провода датчиков — оконечные резисторы + АЦП (норма/тревога/обрыв/КЗ)». Легаси подтягивает вход к неактивному уровню, поэтому обрыв читается как «тихо».
- **Spine:** в AD-15 есть `health: open|short`, но не записано, что проводные контакты подключаются через EOL + АЦП. Без этого значения `open`/`short` у сухих контактов не появятся.
- **Исправление:** в AD-15 добавить: «Проводной контакт — только через EOL и АЦП (ADS1115 или встроенный); прямой GPIO допустим лишь для внутренних сигналов».

### L-2. Автообнаружение: найденный канал «без имени», I²C-мультиплексор
- **Источник:** rules-config: найденный канал появляется в вебе без имени и ждёт настройки; больше двух одинаковых I²C-чипов — только через TCA9548A.
- **Исправление:** дополнить AD-15 одной фразой.

### L-3. Порядок ввода в сеть и значения по умолчанию
- Memlog архитектуры L53: USB в MVP, BLE вторым шагом. В spine оба способа идут равноправно, порядок не записан. Добавить в AD-17 или в Deferred.
- Memlog L43: `leader_priority` по умолчанию одинаковый. Memlog L44: RSSI только подсказка в вебе. Добавить в AD-9 («по умолчанию равный; RSSI в выборе не участвует»).

### L-4. Внутренняя формулировка AD-10 и AD-11
AD-10 гласит «наружу отправляет только `LEADER`», а AD-11 разрешает отправку `FOLLOWER` (страховка) и `ISOLATED`. Это не противоречит входам, но читается как противоречие. Нужно добавить в AD-10 оговорку «кроме случаев AD-11».

## Проверено: совпадает с входами

AP-модель и приоритеты; два класса узлов, коллекторы не голосуют; мягкий лидер с uplink и гистерезисом; 409-арбитраж и уступка; long polling; репликация `offset` и идемпотентность команд; `delivered{event_id, tg_msg_id, pushover_receipt}`; страховка T≈45 с только для критичного; `ISOLATED` и «аварийный режим»; mute не глушит критичное; три уровня конфига и единственный писатель; LWW по HLC на ключ; привязка к железу только манифестом; модель канала; I²C только в корпусе; правила = шаблон + экземпляр + `when` без циклов; все логические узлы считают правила детерминированно; детерминированный ID производного события; полная правка только в локальном вебе; FRAM; HMAC и защита от повтора; зашифрованный NVS, secure boot, подписанный OTA; уведомления о перезагрузке только владельцу с ограничением частоты; повтор длящейся тревоги; неблокирующая работа; запись до подтверждения; языковая конвенция (пользователю — русский).

## Намеренно заменено памяткой архитектуры (не замечания)

JSON → CBOR; ID узла = EUI-64 вместо «наименьшего ID»; ID события `(node, boot, seq)` вместо «узел+счётчик»; лидер по `leader_priority`, затем EUI-64, вместо «наименьшего ID»; коллекторы только Zigbee (изменение лока forge «любой узел ретранслирует через Zigbee или WiFi»); ESP-IDF и новый репозиторий вместо доработки AsyncTelegram2 (правка `timeout:0` становится неактуальной); NVS у коллектора вместо FRAM; LTE/SMS отложены.
